# 多上游 AI 网关技术选型结论

| 项目 | 结论 |
| --- | --- |
| 选型日期 | 2026-07-21 |
| 唯一推荐基础 | `looplj/axonhub` |
| 评估基线 | `ed6119a168483a205a85a2f38c7153f5cf1b61a6`（`unstable`） |
| 推荐集成方式 | 外部 SLA 决策网关 + stock AxonHub 执行数据面 |
| AxonHub 源码侵入 | L0；不修改上游源码 |
| 选型状态 | 通过架构选型；不等同于生产验收 |

## 1. 最终结论

**只选择 AxonHub 作为执行数据面基础。**

没有一个候选项目可以直接满足本项目全部 P0 需求。AxonHub 的优势不是原生覆盖所有 SLA 语义，而是：

1. 多供应商协议转换、流式处理、首内容前顺序回退、容量限制、配额、缓存 Token 成本和逐次执行记录已经存在。
2. 管理 API 和 API Key Profile 足以让外部决策网关在不修改 AxonHub 源码的情况下，逐请求选择一个真实资源。
3. 外部控制组件可以承载本项目特有的价格、余额、缓存、会话、测活、故障域、审计和 SLA 规则，不需要把这些规则写进第三方核心。
4. 其他候选要么许可证直接阻断，要么需要大范围修改请求链和状态模型，不能达到“低上游侵入”的目标。

## 2. 推荐集成边界

### 外部 SLA 决策网关负责

- 维护 `上游站点 → 账号 → Key → 模型/权限 → 地区/故障域` 的真实资源目录。
- 定时查询 NewAPI、Sub2API 及二开版本的模型价格、用户组倍率、Key 倍率、账号余额和 Key 额度。
- 保存价格、汇率、余额、策略和人工覆盖的版本、来源、确认时间及生效时间。
- 按确认余额、在途费用预留和安全储备计算可路由余额。
- 计算资源健康、P50/P95/P99、样本可信度、故障域集中异常、会话前缀 TTFT 和缓存 Token 加权率。
- 在请求前执行能力、数据许可、价格、余额、容量、会话预算、缓存作用域和副作用限制。
- 分配真实业务测活机会，维护探索预算、冷却、再次试错和独立探索账目。
- 在首字提交前观察流，按会话剩余预算取消当前请求或切换稳定资源，并记录所有尝试和重复费用。
- 维护用户体验账目、会话调度账目和全局探索账目，以及 SLA、告警和变更审计。

### AxonHub 负责

- 对外部网关指定的单一资源执行协议转换和上游认证。
- 处理 OpenAI/Anthropic 等协议的流式转发、基础重试、限流和取消传播。
- 保存请求执行、错误、首 Token、Token、缓存 Token、成本和价格引用等原始执行数据。
- 通过管理 GraphQL / Service Account API 接收渠道、Key、Profile 的启停和基础配置变更。

## 3. 资源建模约束

为了满足连续会话缓存率目标，不能把多个真实 Key 放在同一个 AxonHub 渠道内让其自由轮换。推荐：

- 一个真实 Key 配置为一个 AxonHub 渠道。
- 一个真实资源建立一个只允许该渠道的 API Key Profile。
- 外部网关按请求选择 Profile；内部 Profile 凭证不暴露给客户端。
- 共享账号余额、用户组倍率和多个 Key 的关系只在外部权威状态中计算。

这会增加渠道和 Profile 数量，但能保持缓存作用域、账务归因和故障隔离的一致性，且不需要修改 AxonHub 核心。

## 4. 对用户目标的直接回答

| 目标 | 选型后的实现边界 |
| --- | --- |
| 连续会话前缀平均首字时间 ≤10 秒 | 外部网关按每轮实际 TTFT 和剩余预算选择 Profile；AxonHub只执行并回传首字数据 |
| 低价与快速渠道动态分配 | 外部网关按实际成功成本、价格版本、余额和容量选择；AxonHub 全局权重只作慢速调节 |
| 缓存率 ≥90% | 外部网关维护会话/Key/模型缓存亲和和切换损失预测；AxonHub提供缓存 Token 记录 |
| 价格和倍率变动 | 外部采集器形成可信版本，失效或异常时限制路由；管理 API 只同步执行层状态 |
| 账号余额和 Key 余额 | 外部账本维护共享关系、在途预留和安全储备；AxonHub Provider quota 作为辅助证据 |
| 无缝测活 | 使用符合条件的真实业务请求作为探索机会；不依赖固定 `hello`/`ping` |
| 首字前接管 | 外部网关处于同步请求链，观察 AxonHub 流并在提交前取消/切换；AxonHub自身仅提供串行基础回退 |
| 失败和重复费用 | 外部网关记录每次尝试、取消结果、继续计费和上游余额差异；不能只看最终响应 |

## 5. 为什么不能只使用 Webhook 和全局权重

AxonHub 的 Webhook 是渠道自动停用后的异步通知，不是请求前同步决策接口。全局权重也无法同时表达不同会话的 TTFT 余量、缓存归属、租户预算、探索资格和故障域约束。

因此“只部署 AxonHub，再用 Webhook 调权重”不能满足本项目；推荐结构必须让外部 SLA 决策网关位于请求链路。这是本选型的明确前提，也是保持 AxonHub L0 集成的代价。

## 7. 选型生效条件

以下是采用该基础前必须确认的边界，不是本轮开发计划：

1. 对 AxonHub 复合许可证完成法务审查，尤其是不修改 `llm/` 的部署和分发方式。
2. 固定可复现提交，不直接跟随 `unstable`；评估基线为 `ed6119a168483a205a85a2f38c7153f5cf1b61a6`。
3. 证明单资源 Profile 不会把请求路由到未授权渠道，并能保持 Key/模型缓存作用域。
4. 证明流式首字、客户端取消、接管取消、重试尝试和成本回执可以被外部账本完整关联。
5. 明确外部 SLA 决策网关是同步请求路径的必需组件；若不接受这一前提，则本选型不成立。

本结论只回答“选择哪个开源基础及如何保持低上游侵入”，不包含技术栈、开发计划或实施排期。
