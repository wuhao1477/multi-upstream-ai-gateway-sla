# 维护性与上游合并判断

## 1. 判断原则

本项目最重要的维护目标不是减少自有业务代码，而是避免把价格、余额、会话预算、真实业务测活和 SLA 账目写入第三方网关核心。上述能力变化频繁，放入上游请求链会持续产生合并冲突。

## 2. 候选比较

| 候选 | 达到 PRD 所需改动 | 上游升级影响 | 许可证影响 | 维护结论 |
| --- | --- | --- | --- | --- |
| AxonHub | 推荐方式为 L0；外部组件通过管理 API 和单资源 Profile 使用 stock 数据面 | 主要关注 API、Profile、流式行为和数据字段兼容 | 主体 Apache-2.0；`llm/` LGPL-3.0 | 最低上游分叉成本，推荐 |
| bestruirui/octopus | 账号、余额、故障域、测活、账目和告警涉及 L3 | 多个核心模块会长期冲突 | AGPL-3.0 | 不接受 |
| Hureru/octopus | 仍需 relay、Site、日志、账务、健康任务和管理面 L3 改动 | 已与上游形成 424 文件差异，依赖人工同步 | AGPL-3.0 | 不接受 |
| Aether | 技术基础较强，但关键 SLA 语义仍需 L2/L3 | 高频演进，定制边界需持续跟踪 | 未取得商业授权前阻断 | 排除 |
| OmniRoute | 外部插件可完成部分 L1；动态首字预算和账务仍可能进入核心 | Chat 核心与主应用多模块耦合，回归范围大 | MIT | 不作为基础 |
| ccLoad | 无正式插件，补齐领域模型和策略需 L3 | 项目较小，但私有核心改动比例高 | MIT | 不作为基础 |
| zhfeng1/ai-gateway | 接近重写 | 无可复用升级边界 | 无许可证 | 排除 |

## 3. AxonHub 的升级边界

推荐结构不要求向 AxonHub 提交功能 PR，也不要求长期维护私有 fork。升级时只需验证以下外部契约是否保持：

- 标准 OpenAI/Anthropic 等请求与流式响应行为。
- API Key Profile 对渠道、标签和模型的过滤发生在候选排序前。
- 单渠道 Profile 不会切换到未授权渠道。
- 管理 GraphQL / Service Account API 的渠道、Key、Profile、价格和状态操作。
- 客户端取消、首事件等待、错误透传和执行记录语义。
- Request Execution、Usage Log、缓存 Token 和价格引用字段。

价格可信版本、共享余额、故障域、会话状态和 SLA 账目由外部组件持有，因此 AxonHub 数据库变更不会成为这些业务数据的迁移来源。

## 4. 不应提交上游的能力

以下属于本项目的经营和 SLA 规则，不适合要求通用网关上游接受：

- 特定 NewAPI/Sub2API 二开的价格、倍率、余额和账单适配。
- 连续会话前缀 TTFT 预算、缓存率目标和成本策略。
- 探索预算、严格补偿/预算延续和业务测活资格。
- 租户数据许可、故障域定义、业务告警和责任审计。

这些能力保留在外部组件可以独立演进，也避免上游 PR 因业务特异性被拒绝。

## 5. 可提交上游的小范围改进

本次推荐不依赖这些改进。后续若确有必要，只有通用且单一边界的能力适合单独提议，例如：

- 标准 API 的受认证路由提示契约。
- 更严格的“有效首内容”计时语义。
- 配额未知时的可配置保守策略。
- 通用执行事件和更完整的异步 Webhook。

任何需要同时修改候选生成、重试、账务和持久化的提案都不再属于 L2，应停止向网关核心迁移。

## 6. 版本判断

AxonHub 最近发布仍为 beta，评估提交位于 `unstable`。技术选型推荐的是固定提交所代表的架构边界，不是授权自动跟随 `unstable`。正式使用前需固定版本并验证外部契约；本轮未运行候选服务或端到端压测，不把源码可行性等同于生产验收。
