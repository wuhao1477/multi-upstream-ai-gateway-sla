# 维护性与上游合并判断

## 1. 判断原则

本项目最重要的维护目标不是减少自有业务代码，而是避免把价格、余额、订阅计划、到期预测、会话预算、真实业务测活和 SLA 账目写入第三方网关核心。上述能力变化频繁，放入上游请求链会持续产生合并冲突。

## 2. 候选比较

| 候选 | 达到 PRD 所需改动 | 上游升级影响 | 维护结论 |
| --- | --- | --- | --- |
| AxonHub | 推荐方式为 L0；外部组件通过管理 API 和单资源 Profile 使用 stock 数据面，订阅账本完全外置 | 主要关注 API、Profile、流式行为和数据字段兼容 | 最低上游分叉成本，推荐 |
| Aether | 单 Key Routing Group 可 L0 接入；额度字段可采集，但过期过滤、通用订阅决策和动态首内容接管必须外置 | 高频演进；需持续验证路由组、Pool、额度过滤和流式语义 | 优先候选，不作为最终基础 |
| OmniRoute `main` | 单 Connection 白名单 API Key 可受限 L0；额度窗口可作输入，通用订阅、正式 RoutePlan 和 Attempt ID 需外置或 L2 | `main` 与发布分支长期分叉；Chat 核心与主应用多模块耦合，回归范围大 | 可作受限适配，不作为基础 |
| NewAPI | 每真实 Key 独立 Channel + 管理员内部 Token 可 L0；通用外部 RoutePlan 需 L2/L3 | 核心路由和计费高频变化；管理员指定 Channel 不是正式插件契约 | 可作渠道管理平台，不作为基础 |
| Sub2API | 每真实账号独立 Group/API Key 可 L0；OpenAI `Reset` 因子可借鉴，通用订阅、精确账号选择和统一跨平台接管仍需外置或 L2/L3 | 功能面和数据模型大，PostgreSQL/Redis 迁移及平台分支回归范围较广 | 专业化候选，不作为通用基础 |
| Hureru/octopus | 仍需 relay、Site、日志、账务、健康任务和管理面 L3 改动 | 已与上游形成 424 文件差异，依赖人工同步 | 不接受 |
| bestruirui/octopus `master` | 私有 model alias + 单资源拓扑可受限 L0；正式 Channel/Key 契约需 L2，内置完整 SLA 需 L3 | 指定分支无近期提交，并有已确认的状态码、统计和参数覆盖缺陷 | 低优先级适配，不作为基础 |
| ccLoad `master` | 单 Key/URL Channel + 单 Channel Token 可 L0；完整 RoutePlan 需 L2，内置完整 SLA 需 L3 | 项目较小且更新频繁；需持续验证 Token 过滤、流提交、隐藏重试和日志字段 | 轻量 L0 备选，不作为最终基础 |
| zhfeng1/ai-gateway | 接近重写 | 无可复用升级边界 | 排除 |

## 3. AxonHub 的升级边界

推荐结构不要求向 AxonHub 提交功能 PR，也不要求长期维护私有 fork。升级时只需验证以下外部契约是否保持：

- 标准 OpenAI/Anthropic 等请求与流式响应行为。
- API Key Profile 对渠道、标签和模型的过滤发生在候选排序前。
- 单渠道 Profile 不会切换到未授权渠道。
- 管理 GraphQL / Service Account API 的渠道、Key、Profile、价格和状态操作。
- 客户端取消、首事件等待、错误透传和执行记录语义。
- Request Execution、Usage Log、缓存 Token 和价格引用字段。

价格可信版本、共享余额、订阅计划、固定费用分摊、到期预测、故障域、会话状态和 SLA 账目由外部组件持有，因此 AxonHub 数据库变更不会成为这些业务数据的迁移来源。

## 4. 不应提交上游的能力

以下属于本项目的经营和 SLA 规则，不适合要求通用网关上游接受：

- 特定 NewAPI/Sub2API 二开的价格、倍率、余额和账单适配。
- 上游订阅的固定费用、共享额度、有效期、到期未用预测、超额计费及引流上限。
- 连续会话前缀 TTFT 预算、缓存率目标和成本策略。
- 探索预算、严格补偿/预算延续和业务测活资格。
- 租户数据许可、故障域定义、业务告警和责任审计。

这些能力保留在外部组件可以独立演进，也避免上游 PR 因业务特异性被拒绝。

## 5. 可提交上游的小范围改进

本次推荐不依赖这些改进。后续若确有必要，只有通用且单一边界的能力适合单独提议，例如：

- 标准 API 的受认证路由提示契约。
- 更严格的“有效首内容”计时语义。
- 配额未知时的可配置保守策略。
- 通用执行事件和更完整的异步 Webhook。

任何需要同时修改候选生成、重试、账务和持久化的提案都不再属于 L2，应停止向网关核心迁移。

## 6. 版本判断

AxonHub 最近发布仍为 beta，评估提交位于 `unstable`。PRD v1.1 已增量复核到 `2664f459`，确认 Profile 边界仍成立，但 QuotaAware 不能承担订阅到期调度。技术选型推荐的是固定提交所代表的架构边界，不是自动跟随 `unstable`。正式使用前需固定版本并验证外部契约；本轮未运行候选服务或端到端压测，不把源码可行性等同于生产验收。
