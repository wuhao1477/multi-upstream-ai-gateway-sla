## 1bis. M1 基线测试渠道（2026-07-26 确认）

M1 有一条硬验收：同一请求分别**直连上游**与**经我们网关**，把 Responses 的 35 个字段与 reasoning item 逐字段 diff，必须零丢失——这是"字节透传"决策的唯一硬证据（**[AC-26](./14-acceptance-matrix.md)**、[13 §5](./13-research-reassessment.md)）。

| 用途 | 站点 | 家族 | 备注 |
| --- | --- | --- | --- |
| **主基线** | `https://api.lyjxka.top` | NewAPI | 本项目多轮实测用过，Responses 与 `gpt-5.5` 均通（[ISSUE-001](../issues/ISSUE-001-tech-assumption-verification.md)） |
| **对照基线** | `https://muyuan.do` | NewAPI | 2026-07-26 补充，用于交叉验证——避免单站点的私有改动被误判成协议行为 |

> 🔒 **凭证不入库、不入 git**：两站的 key 由运维通过环境变量注入（`deploy/.env`，已在 `.gitignore`）。本表只记录站点与用途。这与 FR-113"一期上游 key 明文存 PG"不冲突——那是**运行时**的渠道凭证，而这里是**测试基线**的配置来源。
>
> **为何要两个站**：单站点的 Responses 实现可能有私有裁剪，只测一个站会把"该站的行为"误认成"协议的行为"。两站结果一致才能确信 diff 结果反映的是我们的透传质量。

## 3. 一期范围的最终形态（S1~S4 确认后）

**做**：上游直连字节透传 · 内容感知 TTFT · 首字前接管（带缓冲上限）· 取消传播 · 按健康/余额/容量/价格/故障域调度 · **会话粘性 + 缓存切换损失预测（FR-056）** · **渠道验证双轨（canary + 主动测活）** · 逐 Attempt 账本 · 价格与余额采集 · 单级 SLA · 管理 API 与二次确认 · 告警落库

**不做（二期）**：订阅制全套 · 多 SLA 等级 · 外部告警通知

> **2026-07-26 调整**：主动测活与缓存切换损失预测**由二期移入一期**（见 §1bis 上方 S1/S2 与 [PRD §2.1](../PRD.md)）。本节此前的旧句已更正。

| 目标 | 一期 |
| --- | --- |
| 前缀平均首字 ≤10 秒 | ✅ 承诺 |
| SLA 前提下降低实际成本 | ✅ 承诺（普通渠道） |
| 调度可解释可追溯 | ✅ 承诺 |
