## 1. 分层判据（三问）

对每条 P0 依次问：

1. **缺了它，系统能不能启动并正确服务一个请求？** → 不能 = **P0-A**
2. **缺了它，会不会造成钱/合规/数据的不可逆损失？** → 会 = **P0-A**
3. **缺了它，系统能跑但会"跑得笨"（选得不够优、省得不够多、看不清）？** → 是 = **P0-B** 或 **P0-C**

| 层 | 含义 | 延期策略 |
| --- | --- | --- |
| **P0-A 骨干** | 不做就**不能上线**：请求跑不通、或会亏钱/违规/丢数据 | **绝不可延**。延期时优先保它 |
| **P0-B 效能** | 系统能安全跑，但**达不到产品目标**（省钱、缓存率、SLA 达标率） | 可延到二期，**须显式降级并告知**（如"暂不做订阅倾斜，接受额度浪费"） |
| **P0-C 运营** | 影响**长期可运营性**（报表、审计、精细告警） | 可延，用简化替代（如日志代替报表） |

## 2. 分层结果（92 条 P0）

### P0-A 骨干（38 条）—— 不做则不能上线

| 域 | FR | 为何不可延 |
| --- | --- | --- |
| 资源身份 | FR-001/002/003/004/005/006 | 没有资源模型就无法路由；能力不匹配会返回错误结果 |
| 价格基础 | FR-010/012/013/018 | 无价格无法算成本；无版本则历史不可复算（**财务不可逆**） |
| 余额安全 | FR-020/021/024/026/031 | **余额判断错会持续烧钱**；Key 失效未识别会全线失败 |
| 容量 | FR-028/029/032 | 无容量控制会打爆上游、触发封禁 |
| 健康基础 | FR-040/042/046/047 | 无健康度就无法避开故障渠道 |
| 会话与首字 | FR-050/051/054 | 首字体验是产品核心目标 |
| 接管与流控 | FR-076/077/078/079/080 | **首字前接管是 SLA 的最后防线**；FR-078 防拼接、FR-079 禁并发重试防重复扣费 |
| 账本 | FR-097/098 | 无逐 Attempt 账本则成本与故障均不可追溯（**不可逆**） |
| 平台底座 | FR-110/111/112/113/114 | 核心可用性、协议、数据边界、Key 存储、规模——地基 |
| 安全边界 | FR-094/096 | Key 不泄露、不偷换模型/不使用不合规渠道 |
| 转向后新增 | **FR-118/119** | 配额未知保守排除（合规）、一次调用=一次上游调用（**记账正确性**） |

### P0-B 效能（36 条）—— 影响产品目标，可显式降级

| 域 | FR | 降级后的后果（须告知） |
| --- | --- | --- |
| 价格精算 | FR-011/014/015/016/019 | 采集半自动、涨跌价不做渐进控流 → 成本优化打折 |
| 余额精细 | FR-022/023/025/027 | 共享余额/信号识别简化 → 余额判断更保守，可用性略降 |
| 订阅全套 | **FR-033~039**（7 条） | **不做订阅台账与倾斜** → 到期额度浪费，"提高订阅利用率"这一业务目标本期不兑现 |
| 健康精细 | FR-041/043/044/045 | 分窗统计/故障域/样本门槛简化 → 调度更粗糙 |
| 缓存与成本 | FR-052/053/055/056/057/058 | 缓存亲和与双倍率不做 → 缓存率目标与成本优化不达标 |
| 测活全套 | **FR-060~067**（8 条） | **不做真实业务测活** → 新渠道靠人工评估，恢复慢 |
| 测活记账 | FR-070/071/072/073/074/075 | 探索预算与补偿模式简化 |
| SLA 统计 | FR-090/091/092 | SLA 指标靠日志聚合，不做实时统计 |

### P0-C 运营（18 条）—— 可用简化替代

| 域 | FR | 简化替代 |
| --- | --- | --- |
| 价格/余额运营 | FR-017 | 价格变化查询 → 直接查库 |
| 告警 | FR-100/101/102/103 | 分级告警 → 先只做 P1 即时通知（余额耗尽/Key 失效/全不可用） |
| 策略变更 | FR-104/115/116/117 | 配置版本化与二次确认 → 一期可先只做 API + 审计日志 |
| 人工控制与审计 | FR-095/099 | 人工停用/变更审计 → 先用 SQL + 操作日志 |
| 数据治理 | FR-093（可选）、FR-105 | 一期默认全允许 |
| 其余运营项 | FR-030、FR-034 等 | 见各域说明 |

> 计数：A 38 + B 36 + C 18 = 92 ✅

## 3. 与里程碑的关系

| 里程碑 | 主要交付层 | 若进度告急 |
| --- | --- | --- |
| M0 骨架 | P0-A | 不可压缩 |
| M1 上游直连 + 账本 | **P0-A 为主** | 不可压缩——账本与透传是地基 |
| M2 流式 SLA 核心 | **P0-A**（接管/首字/取消） | 不可压缩——SLA 核心价值所在 |
| M3 元数据与订阅 | **P0-B 为主**（订阅 7 条 + 价格精算 + 采集） | **首选压缩对象**：可只做价格与余额采集，订阅台账与倾斜延后 |
| M4 经营与验收 | P0-B + P0-C | **次选压缩对象**：测活可延，告警只保 P1，报表用查库替代 |

**结论：进度压力下的砍单顺序 = M4 运营项 → M3 订阅 → M4 测活。M0~M2 不可动。**

---

## 4. 一期最小可上线集（若只保 P0-A）

**能力**：接约 20 个渠道 → 按健康/余额/容量/价格选渠道 → 字节透传执行 → 内容感知首字判定与首字前接管 → 逐 Attempt 账本。

**不具备**：订阅额度优化、真实业务测活、缓存亲和调度、精细告警与报表。

**风险提示**：这是"**能安全省钱地跑**"，不是"**跑得最优**"。产品目标里的"订阅额度有效利用率"与"缓存率 ≥90%"**不会在最小集里兑现**——若采用最小集上线，须对外明确这两项延后。
