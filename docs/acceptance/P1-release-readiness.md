短寿 JWT，今天这把明天多半失效。但这与 2026-08-29 那份归档**不是同一种不可复验**：

- 归档那种：13 个站需人工重登，**没有任何可用凭证**，复跑要人先去登录；

  换一份导出会自己挑出当时还活着的那个。

所以①的复验条件是"有一份新导出"，不是"有人去重登 13 个站"。
⚠️ 若某天导出里**一个 sub2api 令牌都没有效的**，脚本会以退出码 2 明说

### 3.7 采集出站请求只有最小 base_url 校验，完整 SSRF 边界挂到 RBAC（2026-08-29，2026-09-01 修正）

[Codex 二次评审](#附codex-二次评审的两条-high2026-08-29)报的第二条 [high]。

⚠️ **本节 2026-08-29 的原文是错的，2026-09-01 修正。** 原文写着：

> 已修的部分：`validateBaseURL` 收成**一处**、两个入口共用（`createChannel` 与批量导入）。

**"共用"是真的，"收齐了"是假的**，两处都假：

| 原文的说法 | 实际 | 后果 |
| --- | --- | --- |
| 入口只有两个 | 还有第三个 —— **`PATCH /admin/channels/{id}`，一处校验都没有** | POST 拒 `file:///etc/passwd`（400），PATCH 同一个值返 200 **并落库**；建渠道那道闸可被一次 PATCH 完整绕过，此后每轮 sync 都去请求它 |
| 导入侧共用了 | 共用了，但**跑在 `Detect` 之后** | "拒绝落库"拦不住**已经发出的探测请求**，而 SSRF 关心的正是那个出站请求；`dry_run=true` 更是完全走不到落库校验 |

两条都在 2026-09-01 修掉了（见[附二](#附二2026-09-01-自审--codex-三次评审的六条)①④）。校验现在真的在三个入口
之前各跑一次，守卫是 `TestPatchChannelRejectsBadBaseURL` 与
`TestImportValidatesBeforeProbing` —— 后者断言的是 **`Detect` 一次都没被调用**，
而不是"报告里标了 skipped"：后者在"先探测、探完再拒"的实现下**也会绿**。

⚠️ **这条修正本身是本轮最该记下的东西。** 那句"收成一处"不是笔误，是**我写文档时
按自己以为的实现写的**，而 107 项验收跑过 PATCH 的改名/停用/启用，**从没 PATCH 过
`base_url`** —— 于是文档、代码、验收三方各自自洽，缺口从三边中间漏过去。
教训：**"已收敛到一处"这种断言必须数入口，而入口要从路由表数，不是从记忆里数。**

**仍欠的那层**（刻意延后，不是遗漏）：解析后拒绝 loopback / 私有 / 链路本地 /
云元数据网段、自定义 `Transport` 在每次连接前复核 DNS（防 DNS rebinding）、
`CheckRedirect` 拦重定向到不允许的地址。`http://169.254.169.254/…` 是**合法 http
URL，现在照收** —— 这是设计如此，不是漏修（所以那两条守卫刻意**不**把它放进坏值列表：
混进去会让断言在"网段校验没做"时也红，而红的理由就不再是它守的那件事了）。

⚠️ **Codex 2026-09-01 三次评审按 [high] 重提这一条，判定未改。** 它的说法是
「不要把这段最小格式校验作为 SSRF 修复交付」，并建议加一个受限出站客户端
（网段黑名单 + 每次拨号复核解析后的 IP + 重定向逐跳校验）。不做的理由有三条，
前两条是原来那两个前提，第三条是这一轮新查到的事实：

1. 管理面仍是**单一 admin 令牌、无角色分级**，能改 `base_url` 的人已经握有配置面
   本身；`DetectResult` 只回结构化字段（family / version / no_shield /
   quota_per_unit），不回原始响应体，故它不是外传通道。
2. 那层加固的触发条件已经写死在这里：**引入 RBAC 或把管理面暴露到公网，立刻升级
   为阻断项。** 这不是"以后再说"，是一个有判据的挂起。
3. **真库里那行夹具渠道的 `base_url` 就是 `http://127.0.0.1:18099`**（`channel 1`，
   已停用），而 35 项验收里的 3 条 Key 断言全靠它 —— 真渠道的 Key 数恒为 0
   （不变式 N-1），这个靶子不可再生。一刀切拒绝 loopback/私网会让这个靶子**无法
   经 API 重建**，也与「把采集器指向内网地址正是本系统的用途」（真库在
   `<internal-db-host>`）相抵。
   ⚠️ 半套黑名单（只拦 `169.254`、放行 loopback/私网）**更差**：能拿到 admin 令牌
   的人照样能打 `127.0.0.1` 与 `10.0.0.0/8`，于是它买不到任何安全性，只是把
   Codex 举的那个例子从列表里划掉 —— 那是给评审看的，不是给攻击者看的。

**判定影响**：不改①~④任何一条（这一层从来不在四条退出标准里）。它仍是 §3 的一条
已知缺口，且是唯一一条**外部评审两轮都判 [high]、而我两轮都判不阻断**的。

**为什么不阻断发版**：管理面是**单一 admin 令牌、无角色分级**（全仓 `internal/admin`
