### 3.7 采集出站请求只有最小 base_url 校验，完整 SSRF 边界挂到 RBAC（2026-08-29）

[Codex 二次评审](#附codex-二次评审的两条-high2026-08-29)报的第二条 [high]。已修的部分：
`validateBaseURL` 收成**一处**、两个入口共用（`createChannel` 与批量导入）。
原先只有前者查 `http://`/`https://` 前缀，导入侧把导出文件里的 `SiteURL` 直传
`Detect` —— 同一个字段两个入口两套规矩，而更宽的那个恰好是**不经人眼逐条确认的
批量路径**。守卫：`TestImportRejectsBadBaseURL`（`file://` / `ftp://` / 非 URL /
空串各拒一次），反向自验拿掉校验后当场红。

**仍欠的那层**（刻意延后，不是遗漏）：解析后拒绝 loopback / 私有 / 链路本地 /
云元数据网段、自定义 `Transport` 在每次连接前复核 DNS（防 DNS rebinding）、
`CheckRedirect` 拦重定向到不允许的地址。

**为什么不阻断发版**：管理面是**单一 admin 令牌、无角色分级**（全仓 `internal/admin`
无 role/permission 概念），且 `DetectResult` 只回结构化字段（family / version /
no_shield / quota_per_unit），**不回原始响应体** —— 故它不是外传通道。能改 `base_url`
的人已经握有配置面本身；而"把采集器指向内网地址"正是本系统的**用途**（真库就在
`<internal-db-host>`）。

⚠️ **引入 RBAC 或把管理面暴露到公网时，这条立刻升级为阻断项** —— 那时存在一个
"能配渠道但不该能探内网"的角色，上面那层就成了唯一屏障。记在这里而不是某个 issue：
#2/#9 的教训是**挂在 issue 上的欠账会随 issue 关闭一起消失**（§3.6 正是这样翻出来的）。
